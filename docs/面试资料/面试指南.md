# 面试指南

这份文档的目标不是复述源码，而是帮助你把项目讲成“面试官能听懂、能追问、也愿意追问”的样子。

## 1. 适合怎么做项目介绍

### 1.1 30 秒版本

“这是一个把 MySQL、Neo4j 和 LLM 结合起来的订单场景 Agent Demo。MySQL 保存真实业务数据，Neo4j 保存本体结构、实例关系和动作定义。用户提问后，系统会先做意图规划，再走固定图查询或业务动作执行；动作成功后触发增量 ETL，把最新状态同步回图谱。”  

适合先把项目定位讲清楚。

### 1.2 3 分钟版本

“这个项目我主要想解决的是：让自然语言不只用于问答，还能在一个受控业务系统里查结构、查实例、执行动作，并且保证执行后的图谱视图尽快更新。  

系统分三层。第一层是 `order-biz-service`，它基于 MySQL 提供下单、支付、推进阶段、商品管理等真实业务接口。第二层是 `ontology-etl`，它把 MySQL 的表结构映射成 Neo4j 的本体实体、属性和关系，同时把订单实例和动作定义也同步进图谱。第三层是 `ontology-query-service`，它负责自然语言理解、规则规划、LLM 规划、图查询、Agent 工具调用和动作执行。  

实现上，我没有让模型直接生成 SQL 或 Cypher，而是先把用户问题规划成固定的 `queryType`，例如实体查询、关系查询、实例查询或动作执行。查询部分走固定模板，执行部分先从图里读取 `Ont_Action` 的 API 定义，再调用业务服务。动作成功后，会触发增量同步，把 MySQL 最新状态同步回 Neo4j。这样就形成了从自然语言到查询、再到执行、再到图谱更新的闭环。”  

这段话已经覆盖了项目目标、架构、实现取舍和亮点。

### 1.3 5 分钟深讲版本怎么展开

如果面试官愿意继续听，你不要重复“用了哪些技术”，而要按下面顺序展开：

1. 先讲业务目标：不是做聊天，而是做“查询 + 执行 + 回流”的闭环
2. 再讲分层：MySQL 负责事实，Neo4j 负责语义，查询服务负责规划和路由
3. 再讲设计取舍：规则优先，LLM 补位，不让模型直接生成底层语句
4. 再讲动作执行：动作定义入图、UI 卡片确认、执行后增量同步
5. 最后讲不足：事务、状态机、规则收敛、测试

这样讲的好处是，面试官会觉得你理解的是“系统设计”，而不是“我会用几个库”。

## 2. 面试官最容易追问的设计思路

### 2.1 为什么要引入知识图谱

可以这样回答：

“因为这个项目不只是查订单记录，还要回答‘有哪些实体、字段、关系、动作’，这些内容天然更适合图结构表达。图谱让系统能把数据库结构、业务关系和动作元数据统一起来，问答解释性更好。”  

重点不是“图数据库更高级”，而是“更适合表达语义层”。

### 2.2 为什么同时用 MySQL 和 Neo4j

建议这样答：

“MySQL 负责交易事实和业务写入，因为订单、库存、状态更新更适合关系型存储；Neo4j 负责语义表达和查询体验，因为它更适合组织实体、属性、关系和动作。”  

再补一句会更稳：

“我把 MySQL 当权威事实源，把 Neo4j 当问答和语义导航层。”  

### 2.3 为什么没有让 LLM 直接生成 SQL/Cypher

建议这样答：

“我希望模型参与理解，但不直接控制底层查询。因为直接生成 SQL/Cypher 的稳定性和安全性较差，也很难和动作执行、卡片确认、前端结构化返回统一起来。所以我让模型只输出受约束的计划对象，底层查询仍走固定模板。”  

这能体现你的工程控制意识。

### 2.4 为什么动作定义也要入图

建议这样答：

“如果动作只写在业务代码里，问答系统只能查数据，无法理解系统能做什么。把动作建模成 `Ont_Action` 后，查询服务就能统一回答‘某个实体能做什么’，还能根据 `apiPath`、`method` 和 `uiSchema` 做执行路由和表单渲染。”  

这是这个项目最容易打动面试官的点之一。

### 2.5 为什么不直接把实例查询留在 MySQL

建议这样答：

“如果实例只放在 MySQL，确实能保证最新事实，但查询服务就需要在结构解释、关系导航和实例明细之间来回切换存储，整体表达会更割裂。我把实例同步到 Neo4j，是为了让本体层和实例层能在一个查询语义里统一表达；而真实写入还是留在 MySQL，通过增量同步保持最终一致。”  

这能体现你理解了双存储不是重复建设，而是职责分工。

### 2.6 为什么要同时保留规则规划和 LLM 规划

建议这样答：

“规则规划负责高频、确定性强、错误成本高的路径，保证稳定性；LLM 规划负责补规则覆盖不了的表达差异和缺参理解，保证灵活性。两者输出统一计划对象，所以系统既不会完全死板，也不会完全不可控。”  

这句很适合回答“为什么不用纯 Agent”的追问。

## 3. 核心技术实现怎么讲

### 3.1 ETL 实现方式

不要只说“把 MySQL 同步到 Neo4j”，要说清楚三个层次：

1. 结构抽取：读取 `information_schema`，把表和字段变成 `Ont_Entity` 与 `Ont_Attribute`
2. 关系推断：依据 `xxx_id` 命名规则推断表关系，生成 `Ont_Relation`
3. 实例导入：把业务表记录写成 `Demo_*` 节点，并连出实例关系

最好再补充一句：

“动作定义也在 ETL 阶段写入图谱，所以图里不仅有数据结构，还有系统操作能力。”  

如果面试官继续追问“你 ETL 到底做了哪些步骤”，建议展开成：

1. 先从 `information_schema` 抽表和字段元数据
2. 形成中间对象 `TableMeta` / `ColumnMeta`
3. 基于 `xxx_id` 规则推断表间关系
4. 先写 `Ont_Entity`
5. 再写 `Ont_Attribute`
6. 再写 `Ont_Relation`
7. 再补实体直接边
8. 再导入 `Demo_*` 实例图
9. 最后写 `Ont_Action`

这套说法会比“同步 MySQL 到 Neo4j”具体得多。

### 3.2 增量同步实现方式

这里建议强调 checkpoint 设计：

“增量同步不是只记时间戳，而是记 `update_time + id` 两个维度。查询条件是大于更新时间，或者同一更新时间下 `id` 更大。这样可以避免同一秒多条数据写入时发生漏同步。”  

这个细节非常适合体现你考虑过边界条件。

### 3.3 查询服务实现方式

建议从“规划-执行-回答”三段来讲：

1. 规划：`NLQPlanner` 做规则识别，必要时 `LLMPlanner` 补位
2. 执行：`QueryService` 根据 `queryType` 选择固定模板查询
3. 回答：`ChatService` 结合结构化结果和知识库召回生成回答

这样讲比“有很多类”更清晰。

如果你想讲得更像真正做过这个系统，可以再补一句：

“我在查询服务里刻意把‘理解’和‘执行’拆开了。理解阶段只产出计划对象，执行阶段才根据计划选择固定 Cypher 模板或动作执行器。这样出问题时，我能区分是意图识别错了，还是底层执行错了。”  

这句很容易体现系统思维。

### 3.4 动作执行实现方式

建议强调这不是“LLM 直接调接口”：

1. 先识别出执行意图
2. 从图中的 `Ont_Action` 查动作定义
3. 返回 UI 卡片或预填参数
4. 用户确认后调业务服务
5. 执行成功后触发 ETL 增量同步

一句话总结就是：

“执行链路是由图谱驱动的，不是由 prompt 直接驱动的。”  

### 3.5 Agent 实现方式

ReAct 这部分不要说成“万能智能体”，更稳的表达是：

“我给 Agent 限定了工具边界，只允许它在 SQL 只读查询、图查询、受控动作执行和同步动作之间选择。默认还会拦截直接执行意图，优先返回确认卡片。这样可以兼顾多步推理能力和执行安全性。”  

如果面试官继续问“那你为什么还要 Agent”，你可以补一句：

“因为规则适合稳定路径，但不适合所有复杂问题。Agent 在这个项目里不是主执行链路，而是用来处理复杂查询和缺参补全的增强模块。”  

## 4. 面试考点

### 4.1 架构考点

- 为什么分成 ETL、查询服务、业务服务三层
- 为什么用双存储，不做单库方案
- 为什么把动作定义放进图谱
- 为什么执行成功后要做回流同步

### 4.2 数据建模考点

- 如何从关系表映射为图谱实体、属性和关系
- 如何处理实例层和本体层
- 关系推断为什么基于命名约定
- 这种关系推断的边界是什么

### 4.3 Agent / LLM 考点

- 为什么不是自由生成 SQL/Cypher
- 规则规划和 LLM 规划如何分工
- 如何控制 Agent 的工具权限
- 如何降低幻觉和越权执行风险

### 4.4 工程考点

- 增量同步如何避免漏数
- 动作执行后为什么需要最终一致性设计
- 当前系统的事务边界在哪里
- 如果要生产化会先补哪些能力

### 4.5 很容易被深入追问的代码层考点

- `Ont_Entity`、`Ont_Attribute`、`Ont_Relation`、`Ont_Action` 为什么要分开
- 为什么关系既建 `Ont_Relation` 节点，又建实体直连边
- 为什么增量同步 checkpoint 要用 `update_time + id`
- 为什么 `ActionExecutor` 先查图再调接口
- 为什么 `/smart` 和 `/ui/plan` 要做卡片而不是直接执行

## 5. 项目亮点

### 5.1 真正做了闭环

很多项目只是“知识库问答”或者“LLM 调接口”，而这个项目把以下链路串起来了：

- 结构建模
- 实例查询
- 动作执行
- 图谱回流

这是最核心的亮点。

### 5.2 动作元数据图谱化

不是只存“数据是什么”，还存“系统能做什么”。  
这使得图谱既能回答“有什么”，也能回答“能做什么”。

### 5.3 规则优先、模型增强

这说明设计目标是稳定可控，而不是一味追求模型自由度。  
对业务系统来说，这是更成熟的取舍。

### 5.4 有最小知识库增强方案

项目没有依赖复杂外部中间件，而是在 Neo4j 里做全文和轻量 TF-IDF 检索，展示了“先把功能闭环做出来”的工程思路。

### 5.5 UI 卡片与参数预填

执行类意图不是立刻调用接口，而是尽量补齐参数、返回表单、等待确认。  
这个细节能体现你对产品体验和执行安全性的理解。

### 5.6 查询、执行、同步三段闭环是可解释的

很多 Demo 能做事，但解释不清自己为什么这么做。  
这个项目因为中间有计划对象、动作定义和固定模板，所以整条链路是可追踪、可解释的。

## 6. 不足点怎么讲才专业

面试里不要回避不足，但也不要只说“还没做”。最好的方式是“指出问题 + 给出进化方向”。

### 6.1 事务能力不完整

可以这样说：

“当前订单创建、库存扣减、阶段写入是多次数据库写操作，但底层连接是自动提交的，严格来说还没有形成单事务保护。如果后续产品化，我会先补事务边界和失败回滚。”  

### 6.2 状态机约束不足

可以这样说：

“支付和推进阶段目前更偏演示实现，缺少严谨的状态流转校验和幂等控制。生产场景下需要把订单状态机单独抽象出来。”  

### 6.3 配置治理不统一

可以这样说：

“查询服务和业务服务已经支持 `.env`，但 ETL 还在读取硬编码配置，配置源不统一。我会优先把 ETL 也改成环境变量驱动。”  

### 6.4 规则分散

可以这样说：

“当前很多规则和正则散落在 Planner、ChatService 和 App 层，功能增长后维护成本会变高。后续我会把意图规则、补参规则、动作规则统一收敛成独立模块。”  

### 6.5 测试不足

可以这样说：

“目前仓库偏演示项目，核心路径缺少自动化测试。真正继续迭代前，我会补 ETL 映射测试、规划器测试和业务动作回归测试。”  

### 6.6 图谱同步目前是同步阻塞的

可以这样说：

“当前动作成功后会同步触发 ETL，这样做的好处是闭环简单、用户很快能查到新状态，但缺点是请求耗时被 ETL 绑定。生产化我会改成异步任务，让执行成功和图谱追平解耦。”  

## 7. 如果面试官问“你做这个项目最难的地方是什么”

推荐回答：

“最难的不是单独把 Neo4j、MySQL 或 LLM 跑起来，而是把它们接成一个可控闭环。尤其是要同时考虑结构建模、自然语言规划、动作安全执行和执行后的图谱一致性。我最后采用的是规则优先、模板查询、图谱动作定义和增量同步回流这套组合，先把闭环跑通，再逐步增强智能能力。”  

你还可以把“最难”拆成两层来答：

- 第一层难在系统边界：哪些交给 MySQL，哪些交给 Neo4j，哪些交给规划器
- 第二层难在执行安全：怎么既让系统能做事，又不让模型直接乱做事

## 8. 如果面试官问“如果让你继续做，你会怎么演进”

推荐分三步回答：

1. 先补工程底座：事务、状态机、配置中心、自动化测试
2. 再补能力治理：统一 planner 规则、统一动作描述、引入权限模型
3. 最后补智能增强：更强的检索、向量索引、执行审计、会话上下文

这样的回答会显得你不只会做 Demo，也知道如何做产品化演进。

如果想显得更具体，可以继续拆成半年路线：

1. 第一阶段补事务、状态机、配置外部化
2. 第二阶段重构规则中心，统一补参和动作编排
3. 第三阶段把 ETL 改成异步回流，补执行审计
4. 第四阶段再考虑更强的检索和上下文能力

这样会比“我会继续优化”更落地。

## 9. 一些可以直接背的追问回答

### 9.1 如果问“为什么不用单库”

“单用 MySQL，事务没问题，但语义表达弱；单用 Neo4j，关系表达强，但交易写入和状态控制不合适。所以我把 MySQL 当事实源，Neo4j 当语义和问答层，通过增量同步把两者连起来。”  

### 9.2 如果问“为什么不是纯 LLM Agent”

“因为业务系统里错误成本高。我希望模型负责理解，但不直接控制底层查询和执行。高频路径走规则和固定模板，复杂场景再让 Agent 补强，这样更稳。”  

### 9.3 如果问“这个项目最有价值的设计是什么”

“我认为最有价值的是把动作定义也建模进图谱。这样系统不仅知道数据之间的关系，还知道系统具备哪些能力，查询、表单、执行都能围绕同一份元数据组织。”  

### 9.4 如果问“你最不满意的地方是什么”

“我最不满意的是业务写入链路还没有完整事务和状态机约束。这个问题不会影响展示闭环，但会影响真正上线时的数据一致性，所以它会是我优先级最高的重构点。”  

## 10. 可以直接背的亮点总结

“这个项目的亮点有四个。第一，它把 MySQL 业务事实、Neo4j 本体图谱和自然语言规划真正串成了闭环。第二，它没有让模型直接生成底层语句，而是通过受控的计划对象和固定模板保证了稳定性。第三，它把动作定义也建模进图谱，让系统同时具备查询能力和执行能力。第四，执行成功后会触发增量同步，把图谱和业务事实重新对齐。”  

## 11. 一句话收尾

如果你想在最后留一个成熟印象，可以这样收尾：

“这个项目我最满意的不是功能点多，而是把知识结构、查询逻辑、执行能力和数据回流设计成了一个统一系统；同时我也很清楚它目前还是高质量 Demo，下一步重点就是把事务、测试和治理能力补齐。”
