# 项目设计功能实现说明

## 一、项目定位

一个基于知识图谱（Ontology）的智能电商操作系统，核心理念是把数据库的表结构、字段、外键关系、业务 API 自动抽象成"本体语义层"，让用户可以用自然语言进行语义查询和业务操作执行。项目名中的 "Ontology" 指的不是哲学本体论，而是计算机科学中的本体（共享概念模型的形式化规范）。

## 二、整体架构

项目由三个独立的微服务组成：

### 2.1 架构分层

```
用户自然语言 → [ontology-query-service] → 意图识别 → Neo4j 图查询 / 业务 API 调用
                      ↑                        ↓
                 [ontology-etl]           [order-biz-service]
                 MySQL → Neo4j            订单/商品 CRUD
```

### 2.2 ontology-etl（数据同步服务）

职责：把 MySQL 中的表结构、外键关系和业务数据同步到 Neo4j 图数据库。

核心设计思路：

- **表结构提取**：通过 MySQL 的 information_schema 系统表读取所有表的字段名、数据类型、是否可空、主键标记、字段注释等元数据。支持按表名前缀过滤（如只处理 t_ 开头的业务表）。

- **关系推断**：不依赖显式的外键声明，而是通过字段命名约定自动推断实体间关系。规则是：如果字段名以 _id 结尾，去掉后缀后能匹配到另一张表名，就推断为外键关系。例如 order 表的 user_id 字段 → 推断出 Order 对 User 的 REF_user 关系。

- **实体命名**：表名去掉前缀（如 t_）后，按下划线分词并将首字母大写拼接（如 t_order_item → OrderItem）。

- **两层图谱设计**：
  - 模式层：Ont_Entity、Ont_Attribute、Ont_Relation、Ont_Action 节点，描述业务语义模型（有哪些实体、各自有什么字段、实体间什么关系、能执行什么操作）。
  - 实例层：Demo_User、Demo_Order、Demo_Stage、Demo_OrderItem、Demo_Product 节点，存储实际业务数据。

- **动作注册**：系统预定义了多种业务动作（创建订单、支付、推进阶段、浏览商品、补库存、改价、上下架等），每个动作携带 apiPath（API 路径）、HTTP 方法、uiSchema（表单 JSON Schema）写入 Ont_Action 节点。

- **增量同步机制**：使用检查点文件记录每个表的（最后同步时间, 最后同步 ID）游标。每次增量同步从检查点之后读取 MySQL 数据，批量写入 Neo4j。不支持删除检测（仅做 UPSERT）。

- **批量写入优化**：支持配置批量大小，通过 UNWIND 语句批量写入 Neo4j，减少网络往返。

### 2.3 ontology-query-service（语义查询服务）

职责：接收用户自然语言输入，解析意图，查询知识图谱或调用业务 API，返回结构化结果或自然语言回答。

核心设计思路：

**意图识别与规划层**：

- **规则引擎优先**：用大量正则表达式模式匹配中文自然语言查询。支持的意图类型包括：
  - entity：查询实体列表或实体的字段/属性
  - action：查询某实体支持的操作或按关键词搜索动作
  - relation：查询两个实体之间的关系或某实体的所有关系
  - instance：查询具体数据实例（某用户的订单、某订单的阶段历史等）
  - execute：识别为执行意图（下单、支付、推进阶段等）

- **LLM 规划器兜底**：当规则引擎无法确定意图或参数不完整时，调用 LLM（通过兼容 OpenAI 接口的 API）进行意图识别和槽位填充。LLM 被严格约束为只输出 JSON 格式的计划，不输出 Cypher 查询语句。

- **意图路由决策**：ChatService 中的 plan_only 方法实现了规则引擎和 LLM 的智能路由：规则引擎结果置信度高时直接用，参数不完整或意图模糊时才启用 LLM。

**查询执行层**：

- **模式层查询**：将意图转换为 Cypher 图查询语句，查询 Ont_Entity 的属性、Ont_Action 的接口信息、实体间的关系路径等。
- **实例层查询**：同样转换为 Cypher，但查询的是 Demo_* 标签的实例节点，返回实际业务数据。
- **Debug 模式**：返回实际执行的 Cypher 语句和参数，方便开发和调试。

**动作执行层**：

- **本体驱动 API 调用**：从 Neo4j 中查询 Ont_Action 节点获取 apiPath 和方法，通过 HTTP 请求代理调用 order-biz-service 的对应接口。
- **动态表单生成**：根据 Ont_Action 中存储的 uiSchema JSON，在 Web 前端动态渲染操作表单。uiSchema 支持多种字段类型：文本输入、数值输入、商品选择下拉框、商品列表（多选+数量）等。
- **参数智能预填**：在执行动作前，系统通过多种策略自动补全缺失参数——正则从用户输入中提取；针对"某人最近一单"等模式自动查询 MySQL 定位订单 ID；可选启用 ReAct Agent 进行多步推理预填；订单状态预检查（如支付前检查当前阶段）。

**对话服务层**：

- **知识库集成**：支持将文本知识入库到 Neo4j（Ont_Doc / Ont_Chunk 节点），通过全文索引或 TF-IDF 向量检索相关片段，作为 LLM 回答的依据。实现了简单的 BM25 级别的向量检索（自己分词 + TF-IDF 加权 + 余弦相似度）。
- **LLM 答案润色**：将结构化查询结果 + 知识库命中 + 意图计划一起发送给 LLM，生成自然语言回答。LLM 不可用时自动回退到模板化回答。
- **执行后自动同步**：业务操作执行成功后，可选触发增量 ETL 同步，让 Neo4j 中的 Demo 图与 MySQL 保持同步。

**ReAct 推理代理**：

- 实现了完整的 ReAct（Reasoning + Acting）循环，支持多步工具调用。
- 可用工具有四类：sql_query（只读 SQL，白名单+强制 LIMIT）、neo4j_query（通过安全模板查询图谱）、execute_action（执行业务操作）、sync_neo4j（触发增量同步）。
- 提供快速路径对常见简单查询直接执行，跳过 LLM 步骤。快速路径覆盖：实体列表查询、实体字段查询、用户订单查询、订单详情查询、最近 N 单金额聚合、最近一单支付等。
- 适合的查询类型：跨用户比较、聚合统计、条件过滤、多步依赖查询等规则引擎无法处理的场景。

**安全机制**：

- SQL 执行采用白名单制度：只允许 SELECT，只允许预设的表名列表，强制添加 LIMIT 上限。
- 禁止的关键词包括 INSERT/UPDATE/DELETE/DROP/ALTER 等写操作。

### 2.4 order-biz-service（业务操作服务）

职责：提供真实的订单和商品管理 API，是整个系统的"执行层"。

核心设计思路：

- **用户管理**：创建订单时按用户名查找用户，不存在则自动创建（简化设计，非生产级做法）。
- **订单生命周期**：CREATED（创建）→ PAID（已支付）→ SHIPPED（已发货）→ DELIVERED（已签收）。每次阶段变更记录到 t_stage 表形成阶段历史。
- **商品管理**：支持商品列表查询（分用户视图和管理员视图）、详情查询、补库存、改价格、状态管理（上架/下架/缺货/停售）。
- **权限校验**：管理员操作（补库存、改价、上下架）通过查询用户表的 role 字段进行简单的 ADMIN 角色校验。
- **快照机制**：订单商品明细表记录下单时的商品名称和单价快照，避免商品信息变更影响历史订单的准确性。
- **库存扣减**：下单时同步扣减商品库存，并在同一事务中完成。

### 2.5 Web 前端

一个纯 HTML/CSS/JS 的单页应用，暗色主题设计，功能包括：

- 聊天界面：自然语言输入，支持 ReAct 模式开关和 Debug 模式开关。
- 动态表单卡片：根据后端返回的 uiSchema 渲染操作表单，支持商品选择下拉框、商品多选+数量组件、数值输入等。
- 商品浏览轮播：以卡片形式浏览商品列表，支持图片、价格、库存、描述展示。
- 商品详情弹窗：Modal 形式展示商品完整信息。
- 订单详情卡片：展示订单基本信息 + 阶段流程步骤条 + 商品明细轮播。
- 阶段历史卡片：可视化展示订单的阶段流转历史。
- 知识库入库：支持粘贴文本入库到 Neo4j 知识库。
- 快捷按钮：预设常用问题的一键输入。

## 三、数据流全景

1. **初始化**：运行 ontology-etl 全量同步，将 MySQL 表结构写入 Neo4j 模式层（Ont_* 节点），将 MySQL 数据写入 Neo4j 实例层（Demo_* 节点），注册 Ont_Action 动作节点。

2. **语义查询**：用户在 Web UI 输入自然语言 → POST /smart → ChatService.plan_only 进行意图识别（规则优先 + LLM 兜底）→ QueryService 将意图转为 Cypher 查询 Neo4j → 结构化结果 + 可选知识库检索 → LLM 生成自然语言回答 → 返回前端。

3. **业务执行**：用户输入执行类指令 → 意图识别为 execute 类型 → 返回动态表单卡片供用户确认/填写 → 用户提交 → ActionExecutor 调用 order-biz-service API → 执行业务逻辑写入 MySQL → 可选触发 ETL 增量同步 → 返回执行结果。

4. **增量同步**：通过定时任务或 API 触发，ontology-etl 读取检查点 → 查询 MySQL 中 update_time > 检查点的记录 → 批量 UPSERT 到 Neo4j Demo 节点 → 更新检查点。

## 四、关键设计决策

1. **为什么用 Neo4j 而不是纯 SQL 做语义查询？** 图数据库天然适合表示实体-关系-属性这种三元组结构，Cypher 的多跳查询比 SQL 的多表 JOIN 更直观和高效。而且本体模型的灵活性（动态添加关系类型、动作节点）在关系型数据库中需要频繁 ALTER TABLE。

2. **为什么规则引擎优先于 LLM？** 规则引擎零延迟、零成本、结果确定性高。对于模式固定的电商问答场景，正则可以覆盖 80%+ 的常见问法。LLM 作为兜底处理长尾问题，兼顾了性能和智能。

3. **为什么要把 API 也注册到本体中（Ont_Action）？** 这使得"语义理解"和"动作执行"通过同一个知识图谱串联起来。用户问"Order 能做什么"，不仅告诉他有 createOrder/payOrder 等动作，还知道这些动作对应的 API 路径和参数格式。本体成了"活的 API 文档"。

4. **为什么用检查点而非 CDC（Change Data Capture）做增量同步？** 实现简单，不依赖 MySQL binlog 解析等复杂中间件。代价是无法检测删除操作，且依赖 update_time 字段的存在。
