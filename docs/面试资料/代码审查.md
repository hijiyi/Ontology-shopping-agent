# 代码审查

## 1. 审查结论

这是一个结构完整、演示价值很强的 Agent 项目，但当前整体状态更接近“高质量 Demo”，还没有达到生产可用的工程标准。  
我给它的总体评分是 **6.8/10**。

我重点审查了下面几类能力：

- 架构设计是否清晰
- 代码是否便于扩展
- 是否存在明显业务一致性风险
- 是否存在安全与配置风险
- 是否具备继续产品化的基础

## 2. 必须修复

### 2.1 订单创建不是事务，可能写出半成功数据

问题描述：

`create_order()` 内部会依次执行创建用户、创建订单、插入订单项、扣减库存、更新订单金额、写入阶段等多次写操作，但底层 `MySQLDao` 使用 `autocommit=True`。这意味着只要中途某一步失败，前面已经提交的修改不会自动回滚。

影响：

- 可能出现订单已创建但订单项不完整
- 可能出现库存已扣减但订单写失败
- 可能出现订单已生成但阶段记录缺失

证据：

- [mysql_dao.py:L25-L37](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/order-biz-service/dao/mysql_dao.py#L25-L37)
- [order_service.py:L123-L220](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/order-biz-service/service/order_service.py#L123-L220)

修复建议：

- 在 `MySQLDao` 中增加显式事务能力，例如 `begin/commit/rollback` 或事务上下文管理器。
- 让 `create_order()` 整体包裹在单事务中。
- 库存扣减建议改成“带条件更新 + 校验影响行数”，避免并发超卖。

### 2.2 支付和推进阶段缺少状态机与幂等保护

问题描述：

`pay_order()` 不检查订单当前状态，直接把状态改成 `PAID` 并插入一条阶段记录；`advance_stage()` 也允许任意把订单推进到任意字符串阶段。

影响：

- 重复支付会产生重复 `PAID` 阶段
- 非法状态跳转无法被拦截
- 图谱同步后会把这些脏状态进一步放大到查询层

证据：

- [order_service.py:L222-L244](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/order-biz-service/service/order_service.py#L222-L244)

修复建议：

- 引入订单状态机，例如 `CREATED -> PAID -> SHIPPED -> COMPLETED`。
- `pay_order()` 增加幂等校验，已经 `PAID` 的订单直接返回已支付。
- `advance_stage()` 只允许合法转移，并统一维护阶段枚举。

### 2.3 ETL 配置硬编码，存在明显安全与运维风险

问题描述：

`ontology-etl/config.py` 直接写死了 MySQL 和 Neo4j 的地址、账号和密码。

影响：

- 凭据泄露风险高
- 环境切换困难
- 无法和查询服务、业务服务保持统一配置治理

证据：

- [config.py:L4-L18](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-etl/config.py#L4-L18)

修复建议：

- 改成从 `.env` 或系统环境变量读取。
- 区分开发、测试、生产配置。
- 仓库只保留 `.env.example`，不保留真实密码。

## 3. 建议修复

### 3.1 查询、补参和执行规则分散在多个模块，后续演进成本高

问题描述：

执行相关规则不仅在 `NLQPlanner` 中有，在 `app.py`、`ChatService`、`ReActAgent` 中也有大量重复或近似逻辑，例如：

- 是否拦截执行问题
- 最近订单如何补 `orderId`
- 哪些动作允许直接走规则

影响：

- 同一业务规则改动时容易漏改
- 不同入口行为可能不一致
- 面向更多动作扩展时复杂度会快速上升

证据：

- [nlq_planner.py:L127-L299](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/service/nlq_planner.py#L127-L299)
- [chat_service.py:L55-L97](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/service/chat_service.py#L55-L97)
- [app.py:L132-L150](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/app.py#L132-L150)
- [app.py:L490-L660](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/app.py#L490-L660)
- [react_agent.py:L232-L241](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/service/react_agent.py#L232-L241)

修复建议：

- 把执行前补参与动作规则统一抽成独立模块。
- 把“规则规划”“补参策略”“执行拦截策略”拆成可测试组件。
- 入口层只做编排，不承载具体业务判断。

### 3.2 同步逻辑阻塞请求线程，动作成功后的响应时间不稳定

问题描述：

动作执行成功后，`ChatService` 会同步调用 `incremental_sync.py`，并在请求线程内等待结果。

影响：

- 用户执行动作的耗时受 ETL 影响
- ETL 稍慢时会直接拖慢对话接口
- 超时后业务已成功、图谱未更新，用户体验会变差

证据：

- [chat_service.py:L128-L160](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/service/chat_service.py#L128-L160)
- [chat_service.py:L640-L686](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/service/chat_service.py#L640-L686)

修复建议：

- 把增量同步改成异步任务。
- 返回“业务执行成功，图谱同步中”的状态。
- 增加同步任务日志、重试和告警。

### 3.3 动态 SQL 仍然采用字符串拼接，虽然有限制，但模式不够稳

问题描述：

部分“最近一单”“按用户名补订单号”的逻辑通过拼接 SQL 字符串完成，虽然当前对引号做了简单过滤，且 `select_safe()` 只允许 `SELECT` 与白名单表，但本质上仍然是脆弱方案。

影响：

- 规则一旦扩展，注入风险可能重新出现
- 复杂条件拼接时容易出现遗漏
- 可维护性差

证据：

- [app.py:L514-L523](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/app.py#L514-L523)
- [app.py:L603-L612](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/app.py#L603-L612)
- [react_agent.py:L387-L406](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/service/react_agent.py#L387-L406)
- [mysql_read_dao.py:L76-L141](file:///Users/huangjingyue/Desktop/code/Ontology-shopping-agent/ontology-query-service/dao/mysql_read_dao.py#L76-L141)

修复建议：

- 如果是系统内置补参查询，改成参数化 DAO 方法，不走原始 SQL 字符串。
- `select_safe()` 仅保留给 Agent 的受限只读场景。

### 3.4 缺少测试，核心路径回归风险高

问题描述：

仓库当前没有自动化测试目录，也没有针对 ETL 关系推断、Planner 规则、订单状态流转的测试。

影响：

- 改规则后很难确认是否破坏旧问题
- 改 ETL 后很难确认映射是否正确
- 演示环境稳定，扩展时回归风险很高

修复建议：

- 先补 3 类测试：关系推断、意图规划、订单状态流转。
- 对关键正则规则做参数化测试。
- 对 ETL checkpoint 做边界条件测试。

## 4. 可以优化

### 4.1 ETL 和查询服务的配置模式不统一

查询服务与业务服务支持 `.env`，但 ETL 仍然读 `config.py`。从整体项目视角看，这会增加理解和运维成本。

### 4.2 知识库轻量 TF-IDF 方案适合 Demo，但不适合更大规模

当前实现可展示思路，但如果文档量继续增长，需要向真正的 embedding + vector index 迁移。

### 4.3 动作定义当前直接写在 ETL 脚本中

这适合快速演示，但如果动作继续增长，建议拆成独立的动作描述文件或注册表。

## 5. 做得好的地方

### 5.1 架构边界是清晰的

至少在职责层面，ETL、查询服务、业务服务是分开的，没有严重互相缠绕。

### 5.2 没有让模型直接生成 Cypher/SQL 作为主路径

这是一种很好的工程约束，说明项目优先考虑稳定和可控性。

### 5.3 动作定义入图是非常好的抽象

这让查询、执行和前端卡片共用一套元数据，是全项目最有产品潜力的设计之一。

### 5.4 增量同步 checkpoint 设计考虑了同秒数据问题

`update_time + id` 双键方案体现了对边界情况的关注。

### 5.5 ReAct 工具边界做了收缩

虽然还是 Demo，但已经能看到“默认拦截执行、优先卡片确认”的安全意识。

| 架构设计 | 8/10 | 分层清晰，闭环完整，动作入图是亮点 |
| 代码质量 | 6/10 | 可读性尚可，但规则分散，重复逻辑偏多 |
| 潜在 Bug | 5/10 | 事务缺失、状态机缺失会导致真实数据问题 |
| 安全漏洞 | 5/10 | 硬编码凭据明显，动态 SQL 模式偏脆弱 |
| 性能 | 7/10 | 模板查询与批处理思路合理，但同步阻塞请求线程 |
| 可维护性 | 6/10 | 模块职责清楚，但缺测试、缺统一规则中心 |

## 7. 建议的改进顺序

最优先建议按下面顺序做：

1. 先补订单事务与状态机，保证业务正确性。
2. 再治理配置，把 ETL 凭据外部化。
3. 然后收敛规则逻辑，减少 `app.py` / `ChatService` / `Planner` 的重复判断。
4. 最后补自动化测试和异步同步机制。

## 8. 总结

如果把这个项目用于面试展示，它是加分的，因为它确实做出了“图谱 + Agent + 动作执行 + 回流同步”的完整链路。  
如果把它用于继续开发，也完全有价值，因为核心设计方向是对的；只是当前真正需要优先解决的问题，是业务一致性和配置治理，而不是再继续堆更多 Agent 功能。
