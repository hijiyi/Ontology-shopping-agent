# 面试可能问点及答案

---

## 一、项目整体

### Q1：简单介绍一下这个项目？

这是一个基于知识图谱的智能电商操作系统。核心思路是把关系型数据库的表结构、字段、外键关系自动映射为"本体语义层"存储在图数据库中，再通过自然语言理解层让用户可以用中文直接进行语义查询和业务操作。

项目分三个微服务：ETL 服务负责 MySQL → Neo4j 的数据同步和本体构建；查询服务提供意图识别、图谱查询、ReAct Agent、知识库 RAG 等能力；业务服务提供订单和商品的标准 CRUD API。前端是一个完整暗色主题的聊天式交互界面。

### Q2：为什么选择知识图谱而不是纯关系型数据库或向量数据库？

选择知识图谱的核心原因是业务场景的特点：电商系统天然就是实体（用户、订单、商品）+ 关系（归属、包含、引用）+ 属性（名称、价格、状态）的结构，用图来表示比表更直观。

具体对比：
- vs 关系型数据库：SQL 的多表 JOIN 在查询"Order 的所有关系""某用户订单的阶段历史"等问题时，需要多次 JOIN 且 SQL 语句复杂。Cypher 的多跳路径查询天然优雅。
- vs 向量数据库：向量库适合非结构化文本的语义相似度检索，但不适合精确的结构化查询（如"Order 有哪些必填字段""User 和 Order 通过什么键关联"）。两者互补，所以项目中也集成了知识库 RAG 能力。

### Q3：图数据库和关系型数据库在项目中是如何协同的？

MySQL 是写入的真实源，所有业务操作直接写 MySQL。Neo4j 是读取的语义视图，通过 ETL 管道从 MySQL 同步数据并构建本体结构。写操作是 OLTP 路径（MySQL），读操作是语义查询路径（Neo4j）。这是一种 CQRS（命令查询职责分离）思想的简化实践。

## 二、意图识别与 NLU

### Q4：自然语言理解这层是怎么设计的？

采用了三层递进的意图识别架构：

第一层是规则引擎，用大量正则表达式匹配中文自然语言。针对电商场景的常见问法（如"XX有哪些订单""XX和XX什么关系""XX有哪些字段"），直接通过模式匹配完成意图分类和槽位填充。这层零延迟、零成本。

第二层是 LLM 规划器，当规则引擎无法确定意图或参数不完整时，调用 LLM 进行意图识别和参数抽取。LLM 被严格约束为只输出 JSON 格式的计划（包含 queryType、name、slots），不输出 Cypher 查询语句，避免注入风险。

第三层是 ReAct Agent，处理需要多步推理的复杂查询（如"对比两个用户最近三单的总金额""找出最近 20 单中已发货的订单数"），Agent 可以自主调用 SQL 查询和 Neo4j 查询工具，多轮交互后给出最终答案。

### Q5：为什么规则引擎优先于 LLM，而不是反过来？

三个原因：一是延迟，规则匹配是微秒级，LLM 调用需要数百毫秒到数秒。二是成本，规则引擎免费，LLM 每次调用都有 token 消耗。三是确定性，规则引擎的结果是可预测、可调试的，LLM 有一定概率产生错误输出。在电商这种模式相对固定的场景，规则可以覆盖 80%+ 的问法，LLM 作为长尾兜底是合理的工程权衡。

### Q6：如何处理 LLM 输出不可靠的问题？

做了多层防护：第一，LLM 只输出 JSON 计划，不直接输出可执行代码（如 Cypher）。第二，JSON 输出经过严格的字段校验（queryType 必须是指定枚举值、name 必须非空等），校验失败则回退到规则引擎。第三，执行层的 SQL 查询有表白名单、SELECT-only 限制、强制 LIMIT；Neo4j 查询通过预定义的参数化 Cypher 模板执行。第四，"执行"类意图需要用户在表单卡片上确认后才真正调用 API。

## 三、知识图谱设计

### Q7：知识图谱的 Schema 是如何设计的？

分为两层：

模式层定义了四种核心节点类型——Ont_Entity（业务实体，如 Order、User、Product）、Ont_Attribute（实体的字段属性，如 Order.amount）、Ont_Relation（实体间的关系定义，如 Order.user_id → User）、Ont_Action（实体可执行的操作，如 Order.createOrder）。关系类型包括 HAS_ATTRIBUTE、HAS_RELATION、HAS_ACTION、TO 等。

实例层存储实际业务数据，节点标签为 Demo_User、Demo_Order、Demo_Stage 等，通过主键 id 做唯一约束，关系由外键推断而来（如 REF_user）。两层之间通过实体名称的对应关系建立语义关联。

### Q8：如何从 MySQL 表结构自动推断实体关系？

核心逻辑是外键命名约定推断。遍历所有表的所有字段，如果字段名以 _id 结尾，去掉后缀得到基础名称（如 user_id → user），然后尝试匹配已有表名。匹配策略包括：加前缀匹配（t_user）、精确匹配、加复数后缀匹配、末尾包含匹配等。推断出的关系以 REF_ 前缀命名（如 REF_user）。这种方式不依赖数据库显式外键声明，兼容性好，但也受限于命名规范程度。

### Q9：为什么要把 API 也注册到知识图谱中（Ont_Action）？

这个设计让知识图谱从"静态语义模型"升级为"可执行的语义模型"。一个 Ont_Action 节点不仅告诉用户"这个实体能做什么"，还包含了执行所需的所有信息：API 路径、HTTP 方法、参数格式（uiSchema）。前端利用 uiSchema 动态渲染操作表单，实现了"本体驱动的 UI 生成"。新增业务操作不需要改前端代码，只需在 ETL 中多注册一个 Action 节点。

## 四、ReAct Agent

### Q10：ReAct Agent 的实现思路？

实现了标准的 ReAct 循环：系统提示词定义可用工具和规则 → LLM 输出 JSON 决定下一步（调用工具或给出最终答案）→ 执行工具调用获取观察结果 → 将结果反馈给 LLM → 循环直到 LLM 输出最终答案或达到最大步数。

工具包括四类：sql_query（受安全限制的只读 SQL）、neo4j_query（模板化图查询）、execute_action（业务 API 调用）、sync_neo4j（触发 ETL 同步）。工具调用结果以结构化 JSON 的形式返回给 LLM。

额外做了快速路径优化：对于常见简单查询（实体列表、字段查询、用户订单查询、最近 N 单金额聚合等），直接用正则匹配后执行预定义逻辑，跳过 LLM 调用。

### Q11：ReAct Agent 的 Tool Calling 和 LangChain 的有什么区别？

这个项目是轻量级自实现的，不依赖 LangChain 等框架。核心差别在于：LangChain 的 Agent 是一个较重的抽象层，封装了很多中间步骤和 Prompt 模板；而这个项目直接用 HTTP 请求调用 LLM API，手动控制每轮的 JSON 解析、工具执行和消息拼接。

这样做的好处是完全掌控执行流程（如快速路径优化、工具白名单控制），代码量少（约 500 行），没有框架依赖的黑盒问题。代价是需要自己处理 JSON 解析容错、多轮消息管理等细节。

## 五、数据同步

### Q12：MySQL 到 Neo4j 的增量同步是怎么做的？

使用检查点机制。每个表维护一个（last_time, last_id）游标，记录上次同步到的最新记录的 update_time 和 id。每次增量同步执行 `WHERE (update_time > last_time) OR (update_time = last_time AND id > last_id)` 的查询，按时间+ID 排序批量读取，批量写入 Neo4j 后更新检查点并持久化到文件。

这种复合游标设计避免了单纯用时间可能漏数据（同一秒内的多条记录）的问题。也避免了单纯用自增 ID 在分库分表场景下不保证全局有序的问题。

### Q13：ETL 同步的缺点和改进方案？

当前实现有几个问题：不支持删除检测（MySQL 中删除的数据在 Neo4j 中不会消失）；检查点文件无备份；依赖每张表都有 update_time 字段。

改进方向：短期可以增加软删除标记或定期全量对比；长期可以引入 Debezium 等 CDC 工具监听 MySQL binlog，实现真正的实时同步和删除检测。

## 六、安全设计

### Q14：项目在安全方面做了哪些考虑？

首先是 SQL 注入防护。所有 SQL 查询经过多层检查：只允许 SELECT 语句、检测并拒绝 INSERT/UPDATE/DELETE 等关键词、表白名单限制（只能查指定的几张表）、强制添加 LIMIT 限制返回行数。

其次是执行确认机制。自然语言识别为"执行"意图后，不直接调用 API，而是返回一个动态表单卡片让用户确认参数并手动点击"确认执行"。这避免了 LLM 被 prompt injection 诱导执行意料之外的操作。

此外，ReAct Agent 有工具白名单模式，可以在特定场景下限制 Agent 只能使用查询类工具，不能执行业务操作。

### Q15：如果要给这个系统增加认证，你会怎么设计？

在 query-service 和 biz-service 前加一层 API Gateway（如 Nginx 或 Kong），统一做 JWT 验证。用户在前端登录后获得 Token，所有 API 请求携带 Token。权限模型可以分三级：普通用户只能查询和操作自己的订单，管理员可以做商品管理和查看所有订单，超级管理员可以做系统配置。

服务间调用（query-service → biz-service）可以用一个固定服务账号的 API Key 做认证，避免内部接口被外部直接访问。

## 七、知识库 RAG

### Q16：知识库搜索是如何实现的？

提供了两种检索方式：首选是 Neo4j 的全文索引（基于 Lucene），对 Ont_Chunk 节点的 text 字段建了 FULLTEXT INDEX，用 `db.index.fulltext.queryNodes` 过程进行 BM25 相关度检索。如果全文索引不可用，回退到 CONTAINS 子串匹配。

还实现了一个可选的自建向量检索：从 Neo4j 中读取所有 chunk，对中文文本做分词（单个 CJK 字符 + 相邻二元组 + ASCII 单词），构建 TF-IDF 向量和余弦相似度计算。这个实现比较轻量，适合 chunk 数量不大的场景，不需要额外部署 Embedding 模型或向量数据库。通过缓存机制，只在 chunk 有更新时才重新构建向量索引。

### Q17：TF-IDF 向量检索相比 Embedding 向量检索的优缺点？

优点是不依赖外部 Embedding API，零成本、完全本地运行、结果可解释（可以知道匹配上了哪些词）。缺点是语义理解能力弱，同义词、近义词无法匹配（如"支付"和"付款"在 TF-IDF 下是完全不同的词），也无法理解上下文语义。

在面试中可以坦率地说，这个选择是为了在没有 GPU 和 Embedding API 的情况下快速验证 RAG 管道的可行性，生产环境应该替换为 Embedding + 向量数据库的方案。

## 八、工程实践

### Q18：为什么用 Flask 而不是 FastAPI？

Flask 更轻量，对于这个规模的项目足够。FastAPI 的优势（自动生成 OpenAPI 文档、类型校验、异步支持）在这个项目中不是核心需求。选择 Flask 主要是为了快速开发和部署。

如果重新选型，FastAPI 的 Pydantic 模型能让 request/response 的类型定义更清晰，自动生成的 /docs 页面对团队协作也有价值。

### Q19：代码中大量使用了环境变量和 .env 文件，这是好实践吗？

是的。把所有配置外置到环境变量有多个好处：不同环境（开发、测试、生产）可以用不同的值而不用改代码；敏感信息（密码、API Key）不会进入代码仓库；通过 K8s ConfigMap/Secret 或 CI/CD 变量注入也很方便。

项目中每个环境变量都有默认值，本地开发基本可以直接跑，这也是好的工程习惯。

### Q20：如果要部署到生产环境，你觉得还缺什么？

1. 容器化：写 Dockerfile，用 docker-compose 或 K8s 编排 MySQL + Neo4j + 三个服务。
2. CI/CD：GitHub Actions 或其他 CI 工具跑 lint + test + build + deploy。
3. 数据库迁移工具：用 Alembic 管理 MySQL schema 的版本化变更。
4. 监控告警：接入 Prometheus + Grafana，对 QPS、延迟、错误率、数据库连接数等关键指标做监控。
5. 日志聚合：接入 ELK 或 Loki，集中收集和检索日志。
6. API 版本化：在 URL 中加入版本号（如 /api/v1/order/create）。
7. 限流熔断：对 API 做速率限制，服务间调用加熔断器。
8. 测试：至少要有单元测试和 API 集成测试。
