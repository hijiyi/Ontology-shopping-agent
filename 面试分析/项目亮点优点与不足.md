# 面试项目亮点、优点与待优化不足

## 一、项目亮点（面试中重点展示）

### 1. 知识图谱 + LLM 的混合架构

不是简单地套壳 LLM 做聊天机器人。项目有两条路径：规则引擎处理高频确定性查询（零成本零延迟），LLM 处理模糊长尾查询。这种"小模型规则 + 大模型兜底"的工程思想在工业界也越来越主流（如 Apple Intelligence 的端侧+云侧模型分层）。

### 2. "本体即 API 契约"的创新设计

将业务 API 的路径、方法、表单 Schema 全部注册为知识图谱中的 Ont_Action 节点。前端可以完全不硬编码任何表单，纯粹根据 uiSchema 动态渲染界面。这意味着新增一个业务操作只需在 ETL 中注册一个 Action 节点，前后端都无需改代码。

### 3. 从数据库 Schema 自动构建知识图谱

不需要手写任何映射规则，通过读取 MySQL information_schema 和外键命名约定，自动将关系型数据库映射为实体-属性-关系三元组。这在大中型系统中可以显著降低知识图谱的构建成本。

### 4. 完整的 ReAct Agent 实现

不是简单的 function calling 封装，而是实现了标准的 ReAct 循环（Thought → Action → Observation → ... → Final Answer）。Agent 可使用的工具涵盖 SQL 查询（安全白名单）、Neo4j 图查询（模板化安全查询）、业务 API 调用、ETL 同步触发四类，展示了多工具编排能力。

### 5. 多层安全防护设计

- SQL 查询：只允许 SELECT、表白名单、强制 LIMIT、关键词黑名单
- Neo4j 查询：通过预定义 Cypher 模板执行，不接受动态拼接
- 业务执行：通过表单卡片确认机制，避免 LLM 直接触发写操作
- 工具白名单：ReAct Agent 可限制可用工具集合

### 6. 增量数据同步的工程实践

实现了基于检查点的增量同步机制，使用（update_time, id）复合游标避免分页漂移问题。检查点持久化到文件，支持断点续传。

### 7. 自建轻量知识库 RAG

不依赖第三方向量数据库，基于 Neo4j 全文索引 + 自实现 TF-IDF 向量检索，完成了文档入库、文本分块、语义检索、结果注入 LLM 的完整 RAG 流程。分词器还特别处理了中英文混合场景（ASCII 词 + CJK 单字 + 二元组）。

### 8. 意图路由的分层决策

规则引擎 > LLM 规划器 > ReAct Agent 的三层意图处理架构。规则引擎能处理的直接走快速路径（微秒级），参数不完整的升到 LLM 补全，复杂多步查询升到 ReAct Agent。每一层都有明确的升级条件和 fallback 策略。

### 9. Web 前端的工程完整度

单页应用中包含：动态表单渲染（支持商品选择器、数量微调器、多商品列表等复杂组件）、商品详情 Modal 弹窗、订单详情卡片（含阶段步骤条可视化）、商品明细轮播浏览。暗色主题 UI 设计完成度高。

## 二、核心优点

### 架构层面

- **微服务拆分清晰**：ETL、查询服务、业务服务三层职责分明，可以独立部署和扩展。
- **读写分离思想**：业务操作写 MySQL，语义查询读 Neo4j，各司其职。
- **本体层的抽象价值**：模式层和实例层的分离使得"业务语义模型"可以独立于"业务数据"被查询和理解，这是知识图谱的核心优势。
- **低耦合**：服务间通过 HTTP API 通信，ActionExecutor 通过配置文件指定业务服务地址。

### 工程层面

- **Python 类型标注完整**：大量使用 `from __future__ import annotations` + dataclass + Literal，类型安全性好。
- **环境配置规范化**：使用 .env 文件 + 环境变量，关键配置均有默认值。
- **Logging 规范**：各模块统一使用标准 logging 模块。
- **错误处理**：对外 API 统一返回 `{"ok": bool, "error": str}` 格式。

### 业务理解层面

- **订单快照设计**：订单商品明细记录下单时的商品名称和价格快照，而非外键引用，保证了历史订单数据的不可变性。
- **阶段历史追踪**：每次阶段变更写入独立的 stage 表，形成完整的事件溯源。
- **商品状态生命周期**：ACTIVE → INACTIVE / OUT_OF_STOCK → DISCONTINUED，各状态间有业务规则约束。

## 三、待优化不足（面试中坦率承认并说明改进方向）

### 3.1 安全相关（优先级最高）

- **SQL 注入风险**：在智能预填逻辑中，用户名直接拼接到 SQL 字符串中（如 `WHERE name='{user_name}'`）。虽然有引号过滤，但不是根本解决方案。应改为参数化查询。
- **缺少认证授权**：整个系统的 API 没有 Token/JWT 认证，任何能访问服务的人都可以操作订单和商品。生产环境至少需要接入 API Key 或 OAuth2。
- **跨服务调用无认证**：query-service 调用 biz-service 时没有服务间认证机制。

### 3.2 可靠性相关

- **分布式一致性问题**：业务操作写 MySQL 成功后，ETL 同步到 Neo4j 可能失败或延迟，导致用户查询 Neo4j 时看到过期数据。可以考虑在写操作完成后同步触发增量同步，或使用 Outbox 模式。
- **检查点文件无备份**：增量同步的检查点存储在本地 JSON 文件中，丢失后需要全量重刷。
- **缺少事务回滚**：创建订单涉及用户创建、订单创建、商品明细写入、库存扣减等多个 SQL 操作，但没有显式的事务管理（MySQL autocommit=true）。

### 3.3 可扩展性相关

- **硬编码的表结构**：增量同步中的 sync_plan 硬编码了每张表的字段列表，新增业务表需要改代码。应该从元数据中动态读取。
- **正则规则的维护成本**：NLQ 规划器中大量正则表达式难以维护，新增问法需要新增模式。可以考虑用 embedding + 分类器替代部分规则。
- **ReAct Agent 的步数限制**：最大步数硬编码为 5，复杂查询可能不够。可以实现自适应的步数控制。

### 3.4 测试与可观测性

- **缺少任何测试**：无单元测试、集成测试、端到端测试。
- **无监控告警**：没有 Prometheus metrics、健康检查仅返回固定 `{"ok": True}`，不检查数据库连接。
- **无分布式追踪**：跨服务调用没有 trace ID 传递。

### 3.5 知识图谱设计

- **本体质量依赖数据库设计**：关系推断完全依赖 _id 命名约定，如果数据库字段命名不规范（如 order_user 而不是 user_id），关系推断会失败。
- **缺少本体版本管理**：表结构变更后，Ont_Entity 的属性是 UPSERT 而非版本化，无法追溯历史 schema。
- **没有推理能力**：知识图谱仅做了显式关系的存储和查询，没有做传递性推理（如 A→B→C 推导 A→C）。

### 3.6 前端与用户体验

- **单页应用状态丢失**：刷新页面后聊天记录全部丢失，没有持久化。
- **表单提交无加载骨架**：执行操作时仅状态栏显示"执行中..."，缺少骨架屏或进度指示。
- **不支持流式输出**：LLM 回答是一次性返回的，而非逐字流式输出，在长回答时用户等待感明显。
