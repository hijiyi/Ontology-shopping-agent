# 项目总览

## 1. 项目一句话说明

这是一个“面向订单场景的 Ontology Shopping Agent”。它不是单纯做问答，而是把三件事串起来了：

1. 从 MySQL 抽取业务结构和业务数据。
2. 在 Neo4j 中构建可查询、可解释的本体与实例图谱。
3. 基于自然语言完成查询、动作执行和数据回流同步。

换句话说，这个项目的目标不是让大模型“猜答案”，而是让大模型在一个结构化、可执行、可追踪的业务图谱上工作。

## 2. 这个项目究竟要解决什么问题

如果只看功能，它像一个“问订单、查状态、还能执行动作”的系统。  
但从设计目标上看，它真正想解决的是下面这个更难的问题：

“怎样让自然语言既能理解业务结构，又能基于真实业务系统做受控查询和受控执行，而且执行完之后，图谱视图还能尽快追上真实状态？”

这里面其实同时包含 4 个子问题：

1. 系统如何理解业务世界的结构
2. 系统如何把用户问题映射成受控计划
3. 系统如何安全地执行真实动作
4. 系统如何把动作结果重新反映到知识图谱

如果没有这 4 个问题同时成立，这个项目就会退化成下面几种普通系统之一：

- 只会聊天的问答机器人
- 只能查库的报表接口
- 只能调接口的脚本助手
- 只能做静态建模的图谱展示项目

而这个项目的野心，是把这几类能力放进一条统一链路里。

## 3. 为什么要这样设计

如果只用 MySQL 做自然语言问答，会遇到几个问题：

- 表结构语义不明显，模型不容易理解“订单”和“阶段”的业务关系。
- 接口能力是分散在后端服务里的，模型看不到“系统到底能做什么动作”。
- 查询与动作执行之间缺少统一抽象，问答和操作是两套系统。

这个项目的做法是：把数据库表、字段、表间关系和系统动作都提升为图谱中的一等对象。

于是系统里同时存在三层知识：

- 本体层：`Ont_Entity`、`Ont_Attribute`、`Ont_Relation`、`Ont_Action`
- 实例层：`Demo_User`、`Demo_Order`、`Demo_Product`、`Demo_OrderItem`、`Demo_Stage`
- 执行层：业务接口定义、UI 表单定义、动作执行入口、同步回流能力

这样做的结果是：

- 查询更稳定，因为很多问题都落到固定模板而不是自由生成 SQL/Cypher。
- 解释更自然，因为可以围绕实体、属性、关系和动作组织答案。
- 执行更安全，因为系统先识别动作，再根据图中的 `Ont_Action` 找到真实接口。

## 4. 从用户视角看系统体验

如果从用户视角来描述，这个系统其实分成三类使用体验：

### 4.1 看结构

用户会问：

- `有哪些实体`
- `Order 有哪些字段`
- `Order 和 User 什么关系`
- `Product 能做什么动作`

这些问题本质上不是在问“某条订单数据”，而是在问“这个系统世界是怎么定义的”。  
这类问题的答案来自本体层。

### 4.2 看事实

用户会问：

- `Alice 有哪些订单`
- `订单 101 的阶段`
- `订单 101 的商品明细`

这类问题是在问“当前业务事实是什么”，答案来自 Demo 实例层。

### 4.3 做动作

用户会说：

- `给 Alice 下单`
- `支付订单 101`
- `把商品 3 改价到 199`

这类指令不是只要“理解”，还要真正落到业务接口调用上。  
也正因为它有副作用，所以系统必须做参数补全、卡片确认和执行后同步。

## 5. 系统边界

### 5.1 `ontology-etl`

这是“建图服务”。它负责做两件大事：

- 把 MySQL 表结构转成本体结构。
- 把业务表中的实例数据转成 Demo 图节点和关系。

它还顺手把系统支持的动作写进 Neo4j，形成 `Ont_Action`。

### 5.2 `ontology-query-service`

这是“大脑和路由层”。它负责：

- 接收自然语言问题。
- 判断这是“查结构”“查实例”还是“做动作”。
- 需要查图时调用 Neo4j。
- 需要做动作时调用业务服务。
- 动作成功后再触发增量同步，把最新事实写回图谱。

### 5.3 `order-biz-service`

这是“真实业务执行层”。它不理解本体，也不负责自然语言，只负责：

- 创建订单
- 支付订单
- 推进订单阶段
- 商品详情、库存、价格、状态管理

它仍然以 MySQL 为事实源。

## 6. 为什么是“三套表示”，不是“一套到底”

这是理解整个项目的关键。

同一份业务世界，在这个仓库里其实被表示成了三种形式：

### 6.1 MySQL 业务表

它回答的是：

- 真实订单是谁的
- 商品库存还剩多少
- 当前阶段写到哪一步

这里强调的是事务写入和事实准确性。

### 6.2 Neo4j 本体与实例

它回答的是：

- 系统里有哪些实体和关系
- 某个实体有哪些属性和动作
- 实例之间怎么连起来，方便自然语言解释

这里强调的是语义组织和可解释查询。

### 6.3 自然语言计划对象

它回答的是：

- 用户这句话属于什么意图
- 主体对象是谁
- 缺了哪些参数
- 最终应该查还是执行

这里强调的是人话和系统能力之间的桥接。

这三套表示各自解决不同问题，所以项目没有硬把所有责任压到单一存储或单一模型上。

## 7. 整体数据流

### 7.1 建图阶段

第一步，ETL 读取 MySQL 的 `information_schema`，拿到表和字段元数据。

第二步，ETL 根据表名生成实体名，例如：

- `t_user` -> `User`
- `t_order` -> `Order`
- `t_order_item` -> `OrderItem`

第三步，ETL 根据字段名推断关系，规则是：只要列名形如 `xxx_id`，就尝试推断它是否指向另一张表。例如：

- `t_order.user_id` 推断为 `Order -> User`
- `t_stage.order_id` 推断为 `Stage -> Order`

第四步，ETL 把本体结构写入 Neo4j：

- 实体写入 `Ont_Entity`
- 字段写入 `Ont_Attribute`
- 关系写入 `Ont_Relation`
- 额外再创建一条实体到实体的直接关系，便于查询

第五步，ETL 把实例数据写入 `Demo_*` 节点，再根据外键关系把它们连接起来。

第六步，ETL 把系统支持的动作也写入图谱，例如：

- `createOrder`
- `payOrder`
- `advanceStage`
- `restockProduct`
- `updateProductPrice`
- `setProductStatus`

动作节点上还挂了 `apiPath`、`method` 和部分 `uiSchema`，这使得“问答系统”知道系统不仅能查，还能做。

### 7.2 查询阶段

当用户发送自然语言问题时，查询服务不是直接让 LLM 生成图查询，而是先做“规划”。

这里有两层规划：

- 规则规划器 `NLQPlanner`
- LLM 规划器 `LLMPlanner`

默认优先走规则。只有当规则规划信息不足，或者执行动作缺少参数时，才会尝试 LLM 做补充规划。

规划后的结果会落到几种固定意图：

- `entity`：查实体与字段
- `relation`：查实体关系
- `action`：查某实体能执行什么动作
- `instance`：查实例数据
- `execute`：执行真实业务动作

这个设计的好处是，模型不会直接控制底层查询语句，而是只能输出有限类别的计划对象。

### 7.3 动作执行阶段

当规划结果是 `execute` 时，系统并不会立刻胡乱拼 HTTP 请求，而是分三步：

1. 从 Neo4j 的 `Ont_Action` 里查动作定义。
2. 取出 `apiPath` 和 `method`。
3. 通过 `ActionExecutor` 调 `order-biz-service` 的真实接口。

这样做的关键价值在于“动作定义数据化”：

- 新增动作时，可以先更新图谱中的动作定义。
- 前端可以根据 `uiSchema` 自动生成表单。
- 查询服务不必把每个动作的调用细节都写死在代码里。

### 7.4 数据回流阶段

如果动作执行成功，`ChatService` 会执行 `incremental_sync.py`。

这里用的是“业务库仍然是权威源，图谱只是查询和表达层”的思路：

- MySQL 先发生真实变更。
- Neo4j 再通过增量同步追平。

增量同步的 checkpoint 由 `update_time + id` 共同决定，这样能避免“同一秒多条数据更新时间相同”时漏数。

### 7.5 一个最小闭环到底长什么样

如果把这个项目缩成一句最有代表性的流程，那就是：

1. 从 MySQL 抽结构和数据
2. 在 Neo4j 里形成“可问、可解释、可执行”的知识层
3. 用户用自然语言发起查询或动作
4. 系统先规划，再查询或执行
5. 动作成功后把 MySQL 的最新变化同步回 Neo4j

这 5 步就是整个项目的主脉络。

### 7.6 为什么要强调回流同步

很多人第一次看这类系统，会把重点放在“自然语言”和“图谱”上。  
但真正让它从静态展示变成动态系统的，是最后一步回流同步。

因为如果没有回流同步，就会出现下面这种糟糕体验：

- 你刚支付成功
- 下一秒问“这个订单状态是什么”
- 系统还在回答旧状态

所以回流同步不是附属功能，而是“执行系统和问答系统能否统一”的关键。

## 8. 查询服务为什么不直接让 LLM 生成 SQL/Cypher

这是这个项目最值得讲的一点。

原因不是“不会生成”，而是“可控性不够”。

如果直接让模型生成 SQL/Cypher，会有三个问题：

- 容易幻觉出不存在的表、字段和关系。
- 难以控制哪些动作可执行、哪些只能查询。
- 难以做稳定的结果结构化与前端卡片渲染。

所以项目采用了“模型只做计划，不直接做底层语句”的方式：

- 实体、关系、动作、实例查询都映射到固定模板。
- SQL 工具也有限制，只允许 `SELECT` 且限制表白名单与 `LIMIT`。
- 执行动作需要先解析 `Ont_Action`，不允许模型随便造 API。

这是一种典型的“把大模型压缩到受控中间层”的工程思路。

## 9. 这个项目真正的核心亮点，不是某个单点功能

很多项目介绍会把亮点说成：

- 用了 Neo4j
- 接了大模型
- 做了 ReAct

但这都只是技术点，不是核心价值。

这个项目真正的亮点是把下面几个本来分散的能力接到了一起：

### 9.1 结构建模

把表、字段、关系和动作统一建模成知识对象。

### 9.2 稳定查询

把自然语言问题映射到固定计划和固定模板，而不是完全依赖模型自由生成。

### 9.3 真实执行

不是停留在“能回答”，而是能调用真实业务接口做事。

### 9.4 执行后回流

执行不是终点，执行结果还能重新进入图谱，成为下一轮查询的基础。

这四件事同时存在，才让它有面试价值。

## 10. 知识库与 ReAct 的定位

这个项目不只支持图谱查询，还在查询服务里补了两套增强能力。

### 10.1 知识库

查询服务支持把文档切块后写入 Neo4j：

- 文档节点：`Ont_Doc`
- 切片节点：`Ont_Chunk`

检索时优先走 Neo4j Fulltext Index，如果失败，再退化到 `CONTAINS` 检索。

另外还实现了一个轻量级本地 TF-IDF 向量检索缓存。它不是专业向量数据库方案，但足够展示“无外部向量依赖，也能做基础语义召回”的思路。

### 10.2 ReAct Agent

ReAct Agent 的工具集合包括：

- `sql_query`
- `neo4j_query`
- `execute_action`
- `sync_neo4j`

但默认不会让 ReAct 直接执行写操作，除非显式允许。这说明作者已经意识到“Agent 需要边界”，不是把所有能力无差别放开。

它的定位更像：

- 对复杂查询做多步推理。
- 对缺失参数做辅助查找。
- 在“卡片确认执行”模式下做前置补全，而不是完全代替业务系统。

## 11. 站在工程视角，系统最难的地方在哪里

如果只从代码量看，这个项目不算大。  
但它难在要同时协调下面几类边界：

- 结构化知识和非结构化知识的边界
- MySQL 事实源和 Neo4j 语义层的边界
- 查询能力和执行能力的边界
- 规则系统和 LLM 系统的边界
- 用户表达和系统动作之间的边界

真正的设计工作，不是多写几个接口，而是把这些边界划清楚。

## 12. 这个项目最适合怎么讲

如果面试里只能讲 2 到 3 分钟，可以这样概括：

“我做的是一个把知识图谱、自然语言规划和业务动作执行打通的 Agent Demo。底层 MySQL 保存订单事实，Neo4j 保存本体结构、实例关系和可执行动作。用户提问后，系统先做意图规划，再走固定查询模板或动作执行器，避免模型直接生成 SQL/Cypher。动作成功后会触发增量 ETL，把最新业务状态同步回图谱，形成查询和执行的闭环。”  

这段话能同时覆盖：

- 为什么是图谱
- 为什么不是纯聊天机器人
- 为什么要分 MySQL 和 Neo4j
- 为什么要做回流同步

## 13. 当前项目的工程定位

它更像一个“高质量 PoC / Demo 工程”，而不是生产级系统。原因是：

- 有完整的模块边界和清晰链路。
- 已经能演示真实查询与真实动作执行。
- 但事务、配置治理、测试和状态机约束还不够完整。

这恰好适合面试，因为它既能讲出思路，也能讲出不足和下一步演进方向。
