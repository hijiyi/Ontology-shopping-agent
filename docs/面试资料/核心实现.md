# 核心实现

这份文档不按目录机械介绍，而是按“系统是怎么跑起来的”拆解。你可以直接把它当成面试里的技术说明稿。

如果你希望真正把实现讲明白，建议先建立一个总心智模型：

1. `order-biz-service` 负责真实写库，它是业务事实源。
2. `ontology-etl` 负责把“库表结构 + 业务数据 + 动作定义”抽象并同步到 Neo4j。
3. `ontology-query-service` 负责把自然语言映射成查询计划或执行计划，再决定是查图还是调业务接口。
4. 一旦业务动作成功，查询服务再调用 ETL 增量同步，把新事实回写进图谱。

你可以把这个系统理解成三层：

- 事实层：MySQL 里的用户、商品、订单、阶段
- 语义层：Neo4j 里的实体、属性、关系、动作、Demo 实例
- 交互层：自然语言规划、Agent 工具、表单卡片、动作执行

只有先把这三层分清楚，后面每个类的职责才不会混。

## 0. 从一次真实请求看整体实现

### 0.1 查询类请求怎么走

以“`Order 有哪些字段`”为例，请求路径大致是：

1. 前端调用 `ontology-query-service/app.py` 的 `/chat` 或 `/ask`
2. `ChatService` 先调用 `plan_only()`
3. `plan_only()` 先让 `NLQPlanner` 做规则识别
4. 识别结果通常是 `queryType=entity, name=Order`
5. `QueryService.query_entity()` 调固定 Cypher 查询 `Ont_Entity` 和 `Ont_Attribute`
6. `ChatService` 再把结构化结果整理成自然语言

这一条链路里，LLM 最多参与“说话更自然”，而不参与底层查询生成。

### 0.2 执行类请求怎么走

以“`支付 Apple 最近一单`”为例，请求路径会更长：

1. 前端调用 `/smart` 或 `/ui/plan`
2. `ChatService.plan_only()` 先让规则规划器识别执行意图
3. 如果参数不全，比如只有 `userName=Apple`、没有 `orderId`，系统会先尝试补参
4. 补参来源可能是规则、只读 SQL，或者受控 ReAct Agent
5. 系统返回动作卡片，展示 `payOrder` 对应的 UI Schema 和预填参数
6. 用户确认后，前端调用 `/ui/execute`
7. `ActionExecutor` 从 Neo4j 的 `Ont_Action` 中取到 `apiPath=/api/order/pay`
8. 查询服务调用业务服务接口
9. 动作成功后，`ChatService` 触发 `incremental_sync.py`
10. ETL 把 MySQL 最新订单状态同步到 Neo4j

真正难的不是某一步本身，而是把上面 10 步串成可解释、可维护、相对可控的链路。

## 1. ETL：如何把 MySQL 变成 Ontology

### 1.1 先读结构，不先读业务代码

`ontology-etl/main.py` 的主流程很直接，但它背后的设计值得讲清楚：

1. 创建 MySQL 和 Neo4j 连接配置。
2. 从 MySQL 发现符合前缀的业务表。
3. 读取表字段元数据。
4. 读取表数据。
5. 推断表间关系。
6. 把结构、动作和实例写入 Neo4j。

这里的关键不是“把表拷贝到图数据库”，而是先把表结构抽象为图谱本体。

也就是说，ETL 不是单纯的数据搬运，而是一次“结构语义提升”：

- 在 MySQL 里，`t_order` 只是表名
- 在 Neo4j 里，`Order` 被提升成可被解释、可被提问、可被关联动作的实体

这一步决定了后面查询服务能不能用统一方式回答“它是什么、它有哪些字段、它和谁有关、它能做什么”。

### 1.2 如何抽取实体与属性

`MySQLReader` 会读取 `information_schema.tables` 和 `information_schema.columns`。  
抽取出的核心数据结构是：

- `TableMeta`
- `ColumnMeta`

每张表都被解释成一个实体，每个字段都变成实体的一个属性。

例如对 `t_order` 来说：

- 表本身变成 `Ont_Entity{name: "Order", table: "t_order"}`
- 字段如 `id`、`user_id`、`amount`、`current_stage` 会变成 `Ont_Attribute`
- 实体和属性之间建立 `HAS_ATTRIBUTE`

这样做有两个价值：

- 问“Order 有哪些字段”时，不需要读 MySQL 元数据，直接查 Neo4j。
- 后续如果接更多表，也能保持统一表达，不必为每张表单独写解释逻辑。

更细一点看，这里做了三层抽象：

1. MySQL 元数据层：字段原始信息来自 `information_schema.columns`
2. Python 中间对象层：字段被读成 `ColumnMeta`
3. 图谱表达层：字段被写成 `Ont_Attribute`

这样设计的意义在于，中间对象层把 MySQL 读法和 Neo4j 写法解耦开了：

- 如果以后不是 MySQL，而是别的关系库，前半段读取器可以替换
- 如果以后图谱表达发生变化，后半段写入器可以替换
- 中间这层 `TableMeta` / `ColumnMeta` 依然可以复用

这就是典型的“抽取层”和“落库层”分离。

### 1.3 如何推断关系

这个项目没有维护显式外键映射表，而是采用“命名约定推断”。

规则很简单：

- 只要字段名是 `xxx_id`
- 就把 `xxx` 当成候选目标实体
- 再去已有表名中匹配 `t_xxx`、`xxx`、`t_xxxs`、`xxxs`

如果命中，就生成一条 `InferredRelation`。

这类规则的优点是轻量、扩展快，适合演示项目。缺点也很明显：

- 强依赖命名规范。
- 遇到别名字段或复杂外键时不够稳。

所以面试里要主动说明：这是“约定优于配置”的方案，不是完整的数据血缘系统。

这里面还有一个容易被忽略的细节：它并不是直接把 `user_id` 翻译成关系，而是先推断出：

- `from_table = t_order`
- `fk_column = user_id`
- `to_table = t_user`

然后再由 `safe_rel_type()` 把关系名规范化成 `REF_user` 之类的类型。  
这么做的好处是，关系推断和关系命名是两步：

- 第一步先解决“连到谁”
- 第二步再解决“在图里怎么表示”

如果以后你要把 `REF_user` 改成更业务化的 `BELONGS_TO_USER`，只需要改命名策略，不必改推断逻辑。

### 1.4 如何写入 Neo4j

`Neo4jWriter` 会先创建约束，再分批写入：

- `Ont_Entity`
- `Ont_Attribute`
- `Ont_Relation`
- `Ont_Action`

写关系时分两层：

1. 把关系本身建模为节点 `Ont_Relation`
2. 再额外创建实体到实体的直接边

这不是重复，而是为了兼顾两种查询场景：

- 如果要解释关系细节，比如外键字段名，就查 `Ont_Relation`
- 如果只要做实体关系浏览，就直接查实体到实体的边

这属于典型的“解释层 + 遍历层”双表示法。

再进一步看，`Neo4jWriter.write_ontology_structure()` 实际做了四次不同语义的写入：

1. 先写实体节点
2. 再写属性节点，并连 `HAS_ATTRIBUTE`
3. 再写关系节点，并连 `HAS_RELATION -> TO`
4. 最后补实体到实体的直接边

为什么不一次写完？

- 因为每一层依赖不同
- 关系节点要依赖实体已经存在
- 实体直接边又要依赖关系推断已经完成

所以这是一个有顺序的构图过程，不是“把一堆 Cypher 一起跑掉”。

另外，写入时用了分批 `chunked()` 处理属性和关系，这个细节值得讲，因为它说明作者已经考虑到：

- `UNWIND` 一次放太多数据会让单次事务变大
- 批处理比逐条写入效率高
- 但批过大又会影响内存和事务开销

这是一种典型的 ETL 批处理折中方案。

### 1.5 如何写入动作定义

这里是这个项目非常加分的一点。

很多项目把可执行动作写死在业务代码里，但这个仓库把动作也当成图谱对象处理：

- 动作名
- API 路径
- HTTP 方法
- UI Schema

都落成 `Ont_Action` 节点，再通过 `HAS_ACTION` 挂到实体上。

这样前端、规划器和执行器可以围绕同一份动作定义协作：

- 查询“Order 能做什么”
- 渲染动作表单
- 解析调用路径

它的本质是：把“接口描述”也纳入知识图谱，而不是只存业务数据。

这里其实做了一个非常关键的产品抽象：  
把“动作”视为一种和“实体”“关系”同等级的知识对象。

这会直接带来三个后果：

1. 问答系统可以回答“Order 可以做什么”
2. 前端可以基于 `uiSchema` 自动渲染表单
3. 执行器可以从图谱里查动作定义，而不是写死路由表

所以这个项目不是“图谱里存数据，代码里存能力”，而是“图谱里同时存语义和能力定义”。

这是整套方案最有扩展性的点之一。

## 2. Demo 实例层：为什么还要在 Neo4j 再存一份数据

很多人会追问：既然 MySQL 已经有真实订单，为什么还要同步 `Demo_Order`、`Demo_User` 这些节点？

答案是为了让“结构查询”和“实例查询”统一在 Neo4j 中完成。

如果只把结构写进图谱，实例还在 MySQL，就会出现两个问题：

- 自然语言查询时需要同时决定查哪套存储，解释路径更复杂。
- 要讲订单、用户、阶段之间的关系时，不容易利用图遍历能力。

所以项目选择在 Neo4j 中保留一份 Demo 实例层：

- `Demo_User`
- `Demo_Product`
- `Demo_Order`
- `Demo_OrderItem`
- `Demo_Stage`

这样就能直接支持下面这种查询：

- “Alice 有哪些订单”
- “订单 101 的阶段”
- “订单 101 的商品明细”

当然，这也意味着需要处理数据一致性，所以项目又实现了增量同步。

这里还可以再往深处讲一个设计取舍：

- 如果实例只放 MySQL，查询会更“准”，但问答要跨存储做拼装
- 如果实例完全放 Neo4j，问答更顺，但写入一致性压力更大

这个项目最后采用的是“写入以 MySQL 为主、查询解释以 Neo4j 为主”的折中方式。

也就是说：

- 写操作走业务服务 -> MySQL
- 读和解释优先走 Neo4j Demo 图
- 用增量同步保证两边最终一致

这是一种很典型的 CQRS 风格雏形，只不过这里没有把它完全工业化。

### 2.1 实例图是怎么组织的

实例层不是简单地把每张表变成一个节点集合，而是有明确的关系设计：

- `Demo_Order` 通过 `REF_user` 连到 `Demo_User`
- `Demo_OrderItem` 通过 `REF_order` 连到 `Demo_Order`
- `Demo_OrderItem` 通过 `REF_product` 连到 `Demo_Product`
- `Demo_Stage` 通过 `REF_order` 连到 `Demo_Order`

因此像“订单详情”这种问题，本质上不是查一张表，而是做了一次带关系语义的聚合查询。

这正是图数据库在查询表达层的优势。

## 3. 增量同步：如何把 MySQL 更新持续追平到图谱

### 3.1 为什么不能每次都全量

如果每次动作执行后都跑一次全量导入，成本会很高：

- MySQL 全表读取开销大
- Neo4j 写入量大
- 用户执行动作后的等待时间会变长

因此项目提供了 `incremental_sync.py`。

### 3.2 checkpoint 是怎么设计的

checkpoint 不只记录时间，还记录了 `last_id`。

增量查询条件是：

- `update_time > last_time`
- 或 `update_time == last_time 且 id > last_id`

这说明作者考虑过“同一秒多条记录更新时间相同”的问题。  
如果只用时间戳，很容易漏掉同秒内后插入的数据。

### 3.3 同步计划是怎么执行的

同步按固定顺序处理：

1. `t_user`
2. `t_product`
3. `t_order`
4. `t_order_item`
5. `t_stage`

每张表按批次读取，再调用对应的 upsert 逻辑。

这里的实现思路是：

- 用户、商品先同步，给订单和订单项提供依赖节点。
- 订单再连用户。
- 订单项再连订单和商品。
- 阶段最后连订单。

这是一种基于实体依赖顺序的同步策略。

再展开一点，这里的 `Neo4jIncrementalWriter` 没有复用“全量导入 Demo 实例”的逻辑，而是为每张核心表单独写了 upsert 方法：

- `upsert_users`
- `upsert_products`
- `upsert_orders_and_rel`
- `upsert_order_items_and_rel`
- `upsert_stages_and_rel`

这么做虽然代码更多，但换来了两个好处：

1. 每张表更新时可以精确控制要改哪些属性、补哪些关系
2. 增量链路不需要依赖全量表数据，能直接对变更批次做处理

换句话说，全量导入解决的是“第一次建图”，增量同步解决的是“图怎么持续更新”，两者虽然目标类似，但实现策略并不相同。

### 3.4 为什么要用 upsert 而不是 delete + insert

这是一个很适合面试说清楚的点。

如果增量同步采用“先删旧节点，再写新节点”，会有几个问题：

- 关系可能短暂丢失
- 节点 identity 变化可能影响关联查询
- 并发读取时会看到不完整状态

而 `MERGE + SET` 的 upsert 策略能保持：

- 节点主键稳定
- 已有关联尽量延续
- 变更只更新需要更新的属性

所以它更适合这种“持续追平”的场景。

## 4. 查询层：自然语言为什么能稳定落地

### 4.1 规划而不是直接生成

查询服务最关键的设计是“先规划，再执行”。

收到问题后不会直接让模型生成底层语句，而是先产出一个计划对象：

- `queryType`
- `name`
- `intentReason`
- `slots`

这和很多 Agent 系统只做“prompt + tool call”不同，它先把业务世界压缩成可控的中间语义层。

这个中间语义层其实非常重要，因为它把整个系统拆成了两半：

- 上半部分负责理解用户说了什么
- 下半部分负责决定系统到底怎么查、怎么做

只要中间这层计划对象稳定，下半部分就可以持续重构，而不会影响外部表达。

### 4.1.1 计划对象到底解决了什么问题

计划对象至少解决了 4 个工程问题：

1. 避免模型直接生成底层语句
2. 让调试时能看到“系统理解成了什么”
3. 让前端能根据计划决定展示聊天答案还是动作卡片
4. 让规则规划器和 LLM 规划器输出统一格式，便于替换

很多项目的问题在于，模型一旦说错，系统不知道它“理解错了”还是“执行错了”。  
这里因为有显式计划对象，所以可以清楚地区分：

- 理解层错误：`queryType` 或 `slots` 不对
- 执行层错误：查询模板或动作调用失败

### 4.2 规则规划器负责大多数稳定路径

`NLQPlanner` 处理的是高频、确定性强的问题：

- 实体字段
- 动作查询
- 关系查询
- 订单实例查询
- 商品管理动作
- 下单、支付、推进阶段

大量逻辑是通过正则和实体别名映射完成的。  
这看起来“传统”，但优点是：

- 结果稳定
- 便于调试
- 行为可解释

面试里要强调：规则规划不是落后，而是为了把高频路径的可靠性做高。

更具体地说，`NLQPlanner` 做了两类事情：

1. 意图识别：这是查询、实例、关系，还是执行
2. 槽位抽取：比如 `userName`、`orderId`、`stageName`、`productId`

规则规划真正适合的场景是：

- 业务词汇稳定
- 句式有一定规律
- 错误成本较高

订单、支付、阶段推进恰好都符合这三个条件，所以规则优先是合理选择。

### 4.3 LLM 规划器只做补位

`LLMPlanner` 只在规则信息不够、但又需要更灵活理解时介入。

它被要求输出严格 JSON，而且只允许有限 `queryType` 和有限 `task` / `actionName`。

这说明项目对 LLM 的使用是“受约束的增强”，不是“自由代理”。

`LLMPlanner` 的 prompt 里其实给了非常严格的约束：

- 只能输出 JSON
- 只能输出有限的 `queryType`
- `instance` 只能选有限的 task
- `execute` 只能选有限的 actionName

这背后的核心思路是：

- 允许模型帮忙“理解”
- 不允许模型发明系统里不存在的能力

这也是为什么它比“直接让模型写 SQL/Cypher/HTTP 请求”更安全。

### 4.4 QueryService 为什么全是模板

`QueryService` 没有动态生成 Cypher，而是把每种查询都做成固定模板。

例如：

- `query_entity`：查实体和属性
- `query_action`：查实体可执行动作或按动作名模糊查
- `query_relation`：查实体之间关系
- `query_instance`：查订单、阶段、商品明细等实例

这种方式的价值很高：

- 模型不需要生成图库语句。
- 返回结构稳定，便于前端展示。
- 容易做 debug，能直接把模板和参数打印出来。

再往深里说，`QueryService` 其实不是“图数据库访问层”，而是“问题类型到查询模板的映射层”。

例如同样是 `instance`，它内部又会区分：

- 按用户名查订单
- 查用户订单详情
- 按订单号查阶段
- 按订单号查商品明细
- 查某人最近一单的状态

这说明 `queryType` 只是一级分类，真正的业务语义还要靠 `mode` 或 `task` 细分。  
这也是为什么项目里有 `query_instance_by_task()` 这样的实现：  
它不是为了代码好看，而是为了把“自然语言问题的业务子类”显式化。

### 4.5 `app.py` 为什么会比较重

很多人看到 `ontology-query-service/app.py` 会觉得它逻辑偏多，这个判断是对的，但也要理解原因。

它不仅是 Flask 入口，还承担了三类编排职责：

1. 路由层：定义 `/query`、`/ask`、`/chat`、`/smart`、`/ui/plan`、`/ui/execute`
2. 体验层：把执行意图转成动作卡片、表单、预填参数
3. 守门层：控制哪些问题应该阻断执行、哪些可以继续补参

从工程理想状态看，这些逻辑确实应该继续往 service 层下沉。  
但从当前实现看，这里承担的是“交互编排”，不是单纯的 HTTP 控制器。

## 5. 知识库：为什么放在查询服务里

项目支持 `/kb/upsert` 和 `/kb/search`，说明作者想把“结构化图谱”和“非结构化文档”结合起来。

### 5.1 入库方式

文档会先切块，再写成：

- `Ont_Doc`
- `Ont_Chunk`

块之间没有复杂向量索引依赖，先靠全文索引完成基本召回。

### 5.2 检索策略

检索顺序是：

1. 优先走 Neo4j Fulltext Index
2. 失败后降级成 `CONTAINS`
3. 如果打开 `KB_VECTOR_ENABLED`，还可以走本地 TF-IDF 向量检索缓存

这里的亮点不是算法多先进，而是设计很务实：

- 没有强依赖外部向量数据库
- 没有把知识库硬塞进主流程
- 先保证最小可用，再逐步增强

这里还有一个关键设计思路：  
知识库不是拿来替代图谱的，而是拿来补足图谱表达不了的非结构化信息。

比如：

- 图谱适合表达“Order 和 User 的关系”
- 知识库适合表达“异常处理手册”“业务说明文档”“排障建议”

所以在 `ChatService` 里，知识库命中结果是作为 `kb_hits` 挂到结构化结果上的，而不是直接替换掉图查询结果。  
这意味着系统回答时仍然优先基于结构化事实，只在需要补充背景解释时引入文档片段。

## 6. 动作执行：如何做到“能做事，但不完全失控”

### 6.1 动作先从图谱里查定义

`ActionExecutor` 执行动作时，不是 if-else 写死所有接口，而是先查询：

- 动作是否存在
- `apiPath` 是什么
- `method` 是什么
- 是否带 `uiSchema`

也就是说，查询服务是“拿图谱做接口目录”，再路由到真实业务服务。

### 6.2 UI 卡片为什么重要

`/ui/plan` 和 `/smart` 会在执行前尝试返回表单卡片，而不是直接操作。

这说明设计者已经意识到：

- 自然语言执行需要确认
- 参数常常不完整
- 用户应当看到系统准备执行什么

因此系统会做参数预填：

- 从规则中提取参数
- 从最近订单中补出 `orderId`
- 在部分场景下让 ReAct Agent 辅助查询缺失参数

这使得系统呈现出“半自动执行”的产品形态，而不是鲁莽的全自动代理。

更完整地说，动作卡片在这里有 4 个作用：

1. 把执行意图显式展示给用户
2. 把缺失参数转成可编辑表单
3. 把系统补出的参数展示出来，便于用户纠正
4. 把“理解”和“执行”拆成两个阶段，降低误操作风险

所以它不是前端表现层的小优化，而是整套执行安全链路的一部分。

### 6.3 执行成功后为什么要立即同步

如果只执行业务动作，不同步图谱，会出现一个严重体验问题：

- 用户刚支付成功
- 马上再问“订单状态是什么”
- Neo4j 里还是旧状态

因此 `ChatService` 在执行成功后会同步一次 ETL。  
这是整个系统闭环成立的关键。

不过这里也有明显取舍：

- 当前做法优点是简单直接、结果容易解释
- 缺点是同步阻塞请求，执行延迟受 ETL 影响

这就是一个非常适合在面试中体现成熟度的点：  
你既要说“为什么现在这么做”，也要说“如果产品化我会怎么改”。

当前这么做的理由通常是：

- 项目先保证闭环可见
- 用户执行完后能立刻查到新状态
- 实现复杂度最低

而后续演进方向则是：

- 改成异步消息或任务队列
- 把同步结果从强依赖改成状态回执
- 必要时做图谱同步失败补偿

## 7. 业务服务：订单和商品动作到底怎么落地

前面讲的多数是“图谱和查询”，但真正能体现工程含量的，还包括业务服务是怎么被 Agent 驱动的。

### 7.1 `create_order()` 实际做了什么

`OrderService.create_order()` 并不是简单插一条订单记录，它大致做了下面这些事：

1. 先按用户名查 `t_user`
2. 如果用户不存在，就先建用户
3. 创建订单主记录，初始阶段设为 `CREATED`
4. 如果请求带了商品项，就逐个校验商品是否存在、是否上架、库存是否充足
5. 为每个商品项创建 `t_order_item`
6. 扣减商品库存
7. 回写订单总金额和商品数量
8. 最后在 `t_stage` 插入一条 `CREATED`

从业务完整性上看，这已经不是简单 Demo，而是有初步业务链路意识的实现。  
但也正因为步骤多，所以缺少事务会成为核心风险点。

### 7.2 `pay_order()` 和 `advance_stage()` 为什么既简单又危险

这两个方法的实现很直接：

- 更新 `t_order.current_stage`
- 插入一条 `t_stage`

优点是清楚、好演示。  
风险也很明显：

- 没有做状态流转校验
- 没有幂等处理
- 没有统一阶段枚举管理

所以你在面试里可以坦诚地说：

“我在 Demo 阶段优先把执行闭环打通了，但状态机还没收紧，这也是后续最优先要补的地方。”  

这种回答比空泛地说“还有优化空间”更专业。

## 8. ReAct Agent：它解决了什么问题

规则规划对高频路径很好，但对复杂查询、多步取数、带上下文的补参场景有限。

ReAct Agent 的价值就在这里：

- 先思考用户要什么
- 再按工具一步步查询
- 最后整合成答案

可用工具被严格限制为：

- 只读 SQL
- Neo4j 查询
- 受控动作执行
- ETL 同步

而且默认对执行类意图进行拦截，需要走确认卡片。  
这个设计很重要，因为它说明作者没有把 Agent 当成“万能管理员”，而是把它限制在安全边界内。

### 8.1 ReAct 在这个项目里不是主角，而是补强器

很多 AI 项目会把 ReAct Agent 放在最核心位置，但这个仓库其实不是这样。

它真正的主链路是：

- 规则规划
- 固定模板查询
- 图谱动作路由

ReAct 主要用于两类补强场景：

1. 复杂查询需要多步工具组合
2. 执行动作前需要补缺失参数

这说明作者没有把“智能体”当成默认入口，而是当成在边界内发挥价值的增强模块。  
这个定位非常重要，因为它会直接影响系统的稳定性和可调试性。

## 9. 一个端到端例子：从一句话到动作落地

为了把实现讲透，最好能举一个完整例子。  
下面用“`给 Alice 创建一个订单，然后支付最近一单`”来拆。

### 9.1 第一步：创建订单

当用户说“给 Alice 创建一个订单”时，系统会先尝试识别：

- 这是执行类意图
- 目标动作是 `createOrder`
- 当前已知参数可能只有 `userName=Alice`

如果没有完整金额或商品项，系统就不会直接执行，而是返回表单卡片，让用户补齐信息。

当表单提交后：

1. `ActionExecutor` 从 Neo4j 找到 `createOrder` 对应的接口路径
2. 请求发给 `order-biz-service`
3. MySQL 中生成订单、订单项、阶段记录
4. 查询服务触发增量同步
5. Neo4j 中出现新的 `Demo_Order`、`Demo_OrderItem`、`Demo_Stage`

### 9.2 第二步：支付最近一单

用户再说“支付 Alice 最近一单”时，事情就更复杂了，因为这里少了一个明确 `orderId`。

系统会这样处理：

1. 规划器识别为 `payOrder`
2. 发现缺 `orderId`
3. 尝试从规则或 SQL 查询中找到 Alice 最近一单
4. 把查到的 `orderId` 预填进动作卡片
5. 用户确认后执行支付
6. 执行成功后再次触发增量同步
7. 用户再问订单状态时，Neo4j 已经能查到 `PAID`

这个例子正好把项目最重要的 4 个机制都串起来了：

- 意图识别
- 缺参补全
- 动作执行
- 图谱回流

## 10. 这个项目的设计取舍

### 10.1 优先稳定，而不是追求最强智能

项目没有让模型自由生成一切，而是：

- 高频路径规则化
- 查询模板固定化
- 动作定义图谱化
- 工具调用白名单化

这是一种非常工程化的思路。

### 10.2 优先演示闭环，而不是优先生产完备

项目已经把核心链路打通了：

- MySQL -> Neo4j
- Natural Language -> Plan -> Query/Execute
- Execute -> Incremental Sync -> Graph Refresh

但它还没有把事务、测试、配置和状态机做到工业级。

所以如果你在面试里介绍，一定不要把它吹成“生产级 AI 平台”，而要准确说成：

“一个结构完整、链路闭环、具备继续产品化基础的 Agent Demo。”

## 11. 面试里最容易被追问的实现细节

### 11.1 为什么 Neo4j 里同时存本体和实例

回答重点：

- 本体负责解释“系统世界长什么样”
- 实例负责回答“现在业务状态是什么”
- 放在同一个图库里，便于自然语言查询统一落到图结构上

### 11.2 为什么还要保留 MySQL

回答重点：

- MySQL 是交易事实源
- 订单创建、支付、库存变更更适合关系型事务处理
- Neo4j 负责表达语义关系和问答体验

### 11.3 为什么不直接让模型生成 SQL

回答重点：

- 安全性和稳定性不可控
- 返回结构不稳定
- 很难做卡片和后续动作衔接

### 11.4 为什么把动作定义放进图谱

回答重点：

- 让“能查什么”和“能做什么”放在同一套知识层里
- 可以做动作发现、权限扩展、表单渲染和统一路由

## 12. 一句话评价这个实现

这套实现最大的价值，是用很小的技术栈把“图谱建模、问答规划、业务执行、增量回流”做成了一个真正闭环的可演示系统；它最大的不足，是还停留在高质量 Demo 阶段，距离生产级工程还差事务治理、配置治理、测试和状态机约束。
